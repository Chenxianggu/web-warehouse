# 塑料仓库管理系统方案（开发前讨论稿）

> 更新日期：2026-09-14  
> 状态：业务与技术方案；登录与账号基础功能已实现，库存业务功能尚未开发

## 1. 项目目标与已确定前提

建设一个供公司内部使用的 Web 端塑料仓库管理系统，先解决塑料物料、客户信息、出入库和库存查询的日常管理，后续部署到自购云服务器，通过域名访问。

目前已确定：

- **只有一个实际仓库**。第一版界面不做多仓切换，但数据结构保留仓库标识，避免以后增加仓库时重做库存模型。
- **出库允许欠库存**。出库后账面库存可以为负数，系统必须展示欠库数量、原因和操作人；后续入库自动抵消该库存维度的欠数。
- **存在客户寄存货物**。客户所有的寄存货与公司自有货分账管理，即使物料相同，也不能相互抵扣。
- 第一版以电脑浏览器操作为主，兼容平板；暂不把扫码、财务结算和移动 App 作为必需范围。

这里的“负库存”是**账面先出后入**的记录方式，不代表仓库中真的存在负数量的实物。系统需要让管理人员及时核对这种差异。

## 2. 建议的第一版范围

### 2.1 基础资料

| 模块 | 核心内容 |
| --- | --- |
| 物料分类 | 塑料大类，例如 PE、PP、ABS；支持自定义分类。 |
| 物料档案 | 物料编码、名称、牌号、颜色、规格、默认单位、状态、备注。物料编码唯一。 |
| 客户档案 | 客户名称、联系人、电话、地址、状态、备注；用于出库往来和寄存货归属。 |
| 供应商档案 | 供应商名称及联系方式；用于采购或其他来源的入库。 |
| 仓库资料 | 第一版仅一条仓库记录。库位先作为可选字段，不强制启用。 |
| 用户与角色 | 管理员、仓管、业务/查询等角色；具体权限可配置。 |

**分类不等于物料**：例如“PP”是分类，“PP / 某牌号 / 黑色 / 某规格”才是可以独立计库存的物料。客户寄存货的归属也不应通过复制一份物料档案来表达。

### 2.2 库存业务

- **入库单**：记录入库来源、物料、数量、所有权归属、经办人、时间、备注和附件（附件可在第一版后期加入）。
- **出库单**：记录出库去向/客户、物料、数量、从哪一类所有权库存出库，以及是否造成欠库。
- **客户寄存入库与提货**：分别作为“客户所有”的入库与出库；每个客户独立核算。
- **所有权转移**：若客户寄存货转为公司自有货，或公司货转为客户寄存货，使用专门的转移单，留下原归属、目标归属、数量及依据，不能直接修改库存归属。
- **盘点调整**：盘点后通过调整单记录账实差异、调整原因和审批/操作记录。
- **库存查询**：按物料、所有权归属、客户、批次等筛选；显示当前结存、欠库数量和最近变动。
- **库存流水**：可以从每一笔库存变化追溯到原始单据和操作人。

第一版先支持手工录入和筛选。Excel 导入导出可作为第二阶段功能，待确认实际表格格式后实现。

## 3. 库存模型与关键业务规则

### 3.1 库存维度

一条库存余额至少按以下维度区分：

`仓库 + 物料 + 所有权归属 + （可选）批次`

所有权归属有两类：**公司自有**、**客户寄存（指定客户）**。同一个物料在同一个仓库中可以同时存在这两类库存。不同客户的寄存货也要分别记账。

例如：公司自有 PP 500 kg、客户甲寄存 PP 300 kg、客户乙寄存 PP -20 kg，应显示为三条独立余额；不能把三者合并成“PP 总可用 780 kg”用于出库判断。总量可作为汇总统计显示，但必须标明其中包含客户货及欠库。

### 3.2 单据与流水

- 单据采用**草稿 → 已过账**的状态。草稿可修改；已过账单据不直接改数量或删除。
- 已过账单据如果有错，通过**冲销/反向单据**留下更正链，再重新录入正确单据。
- 每个已过账明细生成一条或多条带正负方向的**库存流水**。入库为正、出库为负、归属转移是一出一入。
- 当前库存余额由流水累积得出；为提高查询速度，可以维护余额表，但流水是可审计的记录依据。余额与流水必须在同一数据库事务中更新。
- 单据编号唯一；提交操作需防重复处理，避免浏览器重试导致重复出入库。
- 记录创建人、过账人、时间、操作原因；关键操作另外保留审计日志。

### 3.3 欠库规则

- **允许过账后余额为负**，不在出库时硬性拦截；提交前明确提示预计欠库数量。
- 欠库按完整库存维度计算。例如客户甲寄存货欠 20 kg，客户乙的余货不能替客户甲抵欠。
- 欠库余额在后续同维度入库时自然减少，归零后恢复正库存。
- 库存页提供“欠库清单”，可按物料、客户、形成时间、经办人筛选，并在首页显示欠库笔数与数量。
- 建议将“允许欠库出库”设置为受控权限，普通用户可以录入草稿，由有权限的人过账。这是操作控制建议，不改变已确定的“系统允许欠库”。
- 如果以后启用批次管理，需明确是“按物料总账允许欠库”，还是“指定批次也允许欠库”；第一版默认**批次可选，不强制按批次出库**。

### 3.4 计量与精度

- 第一版建议以 **kg 为库存基准单位**，界面可以输入/显示吨，按 `1 吨 = 1000 kg` 换算；若实际还有“包、袋、卷”等单位，先确定其与重量是否固定换算。
- 数量使用数据库定点小数，不用浮点数计算库存。
- 金额、采购成本、销售价格暂不参与库存计算；若要做财务核算，另设计计价及结算规则。

## 4. 主要操作流程

### 普通入库

选择来源/供应商 → 填写物料和数量 → 选择所有权（默认公司自有）→ 保存草稿 → 核对并过账 → 生成入库流水，增加对应余额。

### 客户寄存入库

选择寄存客户 → 填写物料和数量 → 保存并过账 → 增加**该客户名下**的寄存余额，不增加公司自有余额。

### 普通出库或客户提货

选择出库去向 → 明确使用公司自有货或某客户的寄存货 → 填写物料和数量 → 显示过账后余额及欠库提示 → 有权限人员过账 → 生成出库流水，减少所选归属的余额。

### 寄存货转归属

选择来源归属和目标归属 → 填写物料、数量及转移依据 → 过账时同时生成来源出库与目标入库流水。转移前后实物总量不变，所有权分账发生变化。

### 盘点

查询某物料及归属的账面数量 → 录入实盘数量与原因 → 生成差额调整单 → 过账后留下调整流水。盘点时须区分公司货和各客户寄存货。

## 5. 推荐技术栈与系统结构

| 层面 | 建议 | 选择理由 |
| --- | --- | --- |
| 应用 | Next.js App Router + TypeScript | 前台页面与服务端业务逻辑放在同一项目，适合第一版的规模。 |
| UI | Tailwind CSS + shadcn/ui | 适合管理系统的表格、表单、对话框和侧边导航。 |
| 表单 | React Hook Form + Zod | 录入体验和输入校验；服务端仍需再次校验。 |
| 数据库 | PostgreSQL | 适合单据、关系数据、事务及库存流水。 |
| 数据访问 | Prisma ORM | 数据模型、迁移与常规查询；复杂库存写入仍以事务和数据库约束保证一致性。 |
| 身份认证 | Auth.js | 处理登录与会话；业务角色权限由应用实现。 |
| 部署 | Docker Compose + 反向代理（Nginx 或 Caddy） | 先以单台云服务器部署，域名经 HTTPS 访问。 |

建议采用**单体应用**：浏览器访问 Next.js；Next.js 在服务端完成权限检查、业务校验和数据库读写；PostgreSQL 不直接暴露到公网。管理页面以服务端读取为主，交互表单按需使用客户端组件。出入库过账等写操作集中在业务服务中，不把库存计算散落在各个页面。

第一版不引入 Redis、消息队列、微服务或独立后端。以后若出现大量导入任务、扫码设备对接或第三方系统集成，再按具体需求增加。

## 6. 主要数据实体（概念设计）

| 实体 | 作用与重要字段 |
| --- | --- |
| 用户、角色、权限 | 登录身份、角色、是否可过账/冲销/允许欠库/查看报表。 |
| 客户、供应商 | 往来对象；客户同时可作为寄存货所有者。 |
| 物料分类、物料 | 塑料分类与可计库存的具体物料。 |
| 仓库、库位 | 第一版一个仓库；库位可选。 |
| 批次 | 可选的批号、到货日期等信息；先保留扩展能力。 |
| 库存单据、单据明细 | 类型、状态、来源/去向、所有权、数量、时间、经办人、备注。 |
| 库存流水 | 每次已过账的正负数量变化、归属维度、来源单据。 |
| 库存余额 | 按库存维度聚合的当前数量，可为负数。 |
| 操作审计 | 关键操作、操作者、时间及更正原因。 |

数据库约束至少保证物料编码、单据编号唯一，明细数量大于零，归属为“客户寄存”时必须指定客户。数据库迁移文件纳入版本管理。

## 7. 页面规划与角色

建议页面：首页概览、物料管理、客户管理、供应商管理、入库单、出库单、寄存货管理、归属转移单、盘点调整、库存查询、库存流水、欠库清单、用户与权限。

| 角色 | 第一版建议权限 |
| --- | --- |
| 管理员 | 基础资料、用户权限、全部单据和报表；可冲销。 |
| 仓管 | 录入和过账出入库、盘点、查询库存；是否允许欠库过账可单独授权。 |
| 业务人员 | 查看相关客户与库存、录入草稿；默认不能直接过账和冲销。 |

角色仅是初始建议。具体用户能看哪些客户、谁能审批或过账，应在开发前结合实际人员分工确定。每个服务端写入口都要检查身份与权限。

## 8. 部署、备份与运维

- 开发环境与正式环境使用独立数据库；正式环境通过环境变量提供数据库连接和登录密钥，不把密钥提交到仓库。
- 服务器上运行 Next.js 和 PostgreSQL，前置 Nginx/Caddy 做 HTTPS 与反向代理；数据库端口仅对内部网络开放。
- 配置自动数据库备份，并定期验证备份能恢复。单据和库存流水是核心业务数据，备份优先级高于页面文件。
- 上线后监测服务可用性、磁盘空间、数据库容量、备份结果和应用错误。
- 若使用中国大陆服务器及域名对外提供网站，购买时预留备案办理时间，并以服务器服务商与主管部门的实际要求为准。
- 初期按单机部署设计，但保持应用配置和数据库迁移可重复执行，便于以后迁移服务器。

## 9. 建议开发顺序与验收重点

1. **业务确认与原型**：确定物料编码规则、入出库字段、寄存货单据、计量单位和权限；画出关键页面原型。
2. **基础资料与登录**：物料、客户、供应商、用户角色。
3. **库存核心**：入库、出库、客户寄存、归属转移、流水、余额与欠库提示。
4. **核对能力**：盘点、冲销、查询筛选、欠库清单、审计日志。
5. **上线准备**：数据初始化、权限复核、备份恢复、部署与使用说明。

核心验收场景：

- 同一物料的公司货、客户甲寄存货、客户乙寄存货分别显示；客户甲出库不会消耗其他归属的余额。
- 余额 10 kg 时出库 15 kg，可以过账并显示 -5 kg；后续同归属入库 8 kg 后显示 3 kg。
- 重复点击或网络重试不会生成两张已过账单据。
- 已过账单据不能直接删除；冲销后能追溯原单、冲销单和库存变化。
- 并发提交出入库时，流水汇总与余额一致。
- 非授权用户不能通过直接请求服务端接口完成过账或冲销。

## 10. 开发前仍需确认的业务细节

这些问题不妨碍确定技术栈，但会影响字段、页面和具体规则：

1. **批次是否必须管理**：目前方案按“批次可选”设计。是否要记录厂家批号、生产日期、到货批次，出库时是否指定批次？
2. **寄存货欠库规则**：本方案允许任何库存归属形成负余额，但建议客户寄存货欠库单独授权，并在单据中记录原因。实际是否这样执行？
3. **计量单位**：是否统一按 kg，是否会按吨、袋、件录入，袋/件与重量的换算是否随物料变化？
4. **出库去向**：公司货出库是否一定关联客户？是否存在内部领用、损耗、退货、调拨等场景？
5. **单据管理**：过账前是否需要二人审批？是否要上传磅单、送货单等附件？
6. **历史数据**：上线时是否需要导入现有 Excel 物料、客户及期初库存？
